## Purpose & Scope
Контракт реализованной автоматической слоговой партии BL-002 и правки BL-012 непосредственно над нотами. Пользовательские решения и примеры — @docs/syllable-score-v1.md. Основной потребитель — настольная студия.
Первая область — ведущий голос простых песен EN/RU. Роли, наложенные голоса и заливка BL-003 отложены. Исходная мелодия и аудио сохраняются. Поручение от 14 сентября 2026 года разрешает реализацию T1–T7 и реальную проверку Sputnik/Mujuice.
## Surface
Существующие модули: @src/karaoke_generator/syllables.py, @src/karaoke_generator/learning_v3.py, @src/karaoke_generator/manual_lyrics.py, @src/karaoke_generator/manual_web.py, @src/karaoke_generator/static/studio.js и @src/karaoke_generator/static/manual-model.js.
Модули слоговой партии: `src/karaoke_generator/syllable_score.py` для сборки и `syllable_score_storage.py` для версий. Старые schema-3/ручные форматы остаются отдельными.
### Данные schema 1
| Поле `syllable-score.json` | Содержание |
|---|---|
| Заголовок | `schema_version=1, job_id, source, base_analysis_key, revision, canonical_text, provenance` |
| `source` | SHA-256 аудио, вокала, TXT и неизменяемого набора нот; длительность; язык |
| `occurrences[]` | `occurrence_id, source_word_id, source_text, source_ranges, unit_ids[]`; конкретное исполнение, не написание слова |
| `units[]` | `unit_id, occurrence_id, kind=syllable\|word_fallback, text, order, source_ranges, start/end, intervals[], segmentation_status, timing_status, origin, reason_codes[]` |
| Идентичность слога | Для `kind=syllable` поле `unit_id` является syllable_id; импортированный annotation_id хранится в provenance |
| `intervals[]` | `{start,end,support}`; support: `note_link` либо `unpitched`; конечные неперекрывающиеся активные интервалы; start/end unit — их охватывающие границы |
| `note_links[]` | `link_id, unit_id, source_note_id, start/end, continuation, origin`; интервал связи внутри ноты и интервала unit |
| `unresolved[]` | unit/link ID либо исходное слово, код причины, текст и конфликтующие кандидаты; кандидаты не входят в действующие связи |
| Статусы | segmentation/timing: `suggested\|approximate\|unavailable`; origin: `automatic\|manual\|legacy`; качество и авторство независимы |
| `source_ranges` | Диапазоны Unicode codepoints в неизменном canonical_text; ручное несовпадение хранит `manual_override` и исходный текст |
| `provenance` | Версии алгоритмов/параметры, source cache SHA, imported IDs, причины fallback и базовая ревизия |
Для unplaced start/end равны null и intervals пуст; note_links отсутствуют. У неприкреплённого к нотам, но имеющего время слога intervals сохранены. Ручное изменение не создаёт эталон.
### API и хранение
Префикс `/api/studio/jobs/{id}/syllables`. GET возвращает `status, operation_id, published, draft`; неизвестный job — 404; без подготовки status=not_prepared.
POST с `{request_id, retry:false}` явно готовит отдельный автоматический кандидат; готовый совместимый ответ — 200, queued/running — 202 с operation_id. Повтор request_id с тем же телом не дублирует работу; с другим телом — 409.
PUT с `{request_id, base_revision, document}` сохраняет ручной документ; 200 возвращает новую revision, конфликт — 409, нарушение схемы/времени — 422, ошибка хранения — 507.
`status=not_prepared|queued|running|ready|partial|failed|interrupted`. published содержит immutable key/URL автоматического результата; draft — ручную ревизию на конкретной базе. Ошибка операции не удаляет прежние published/draft.
Каталог `result/syllable-score/`: `auto/<key>/syllable-score.json`, `revisions/<revision>.json` и атомарный index. База ручной правки фиксирует идентичность notes и анализа; новые автоматические кандидаты не переключают её молча.
GET артефакта `/artifacts/{key}/syllable-score.json` отдаёт только опубликованный файл; GET ручной ревизии `/revisions/{revision}` отдаёт сохранённый документ. Неизвестный ключ/ревизия — 404.
## Normative Behavior
1. WHEN анализ создаёт подписи, builder MUST брать автоматическое написание из TXT.
2. WHEN builder предлагает слоги, builder MUST сохранить их порядок и принадлежность исполнению слова.
3. WHEN доступны пригодные CTC-границы, mapper MUST использовать их для временных кандидатов.
4. IF внутренние границы сомнительны, THEN mapper MUST отметить приблизительное размещение.
5. IF состав слогов неизвестен, THEN builder MUST создать одно word_fallback.
6. WHEN слог пересекает несколько нот, mapper MUST сохранить один unit_id и несколько связей.
7. WHEN нота содержит несколько слогов, mapper MUST разделить только текстовые временные области.
8. WHEN renderer показывает распев, renderer MUST вывести слог у начала и «─» над последующими связанными нотами.
9. WHEN начало распева вне вида, renderer MUST повторить текст у первого видимого продолжения как опору чтения.
10. WHEN слог не имеет ноты, builder MUST сохранить его без фиктивного события.
11. WHEN неподписанная нота видна, renderer MUST сохранить её и контур без «Нет текста».
12. WHEN пользователь включает коррекцию, UI MUST редактировать подписи на существующей нотной шкале.
13. WHEN пользователь вводит слог, editor MUST применить одну отменяемую операцию.
14. WHEN пользователь меняет общий слог, editor MUST обновить все его связи.
15. WHEN пользователь назначает другой слог одной области, editor MUST изменить только выбранную связь.
16. WHEN пользователь разбивает слово, editor MUST показать предпросмотр состава и размещения перед применением.
17. WHEN число слогов отличается от числа областей, editor MUST потребовать явное распределение.
18. WHEN пользователь объединяет слоги, editor MUST ограничить объединение соседями одного occurrence.
19. WHEN пользователь удаляет подпись области, editor MUST сохранить ноту и остальные связи.
20. WHEN пользователь сохраняет правку, storage MUST атомарно проверить и повысить revision.
21. WHEN повторяется успешный PUT request_id, API MUST вернуть прежний результат без повторного повышения revision.
22. WHEN запускается новый анализ, storage MUST сохранить ручной результат на прежней базе.
23. WHEN старый проект открывается, adapter MUST сохранить его исходный формат без молчаливого преобразования.
24. WHEN текущий слог определяется, UI MUST использовать intervals, а не охватывающий паузы start/end.
25. WHEN данные сменились, UI MUST проверять job_id, base_analysis_key и revision до применения ответа.
26. WHEN связь удалена или переназначена, editor MUST атомарно нормализовать intervals, start/end и continuation.
27. WHEN открыт пункт нерешённых мест, editor MUST предоставить правку текста и времени без обязательной ноты.
## Constraints & Invariants
- Builder MUST NOT приравнивать количество слогов к количеству нот, букв или pitch-переходов.
- Mapper MUST NOT заполнять паузы и далёкие ноты контекстным словом; приблизительность не скрывает отсутствие связи.
- Auto ranges MUST восстанавливать исходное слово без дублирования продолжений. Ручное несовпадение помечается отдельно.
- Validator MUST проверять уникальность ID и все ссылки. Ссылка имеет `0≤start<end≤duration` и содержится в своей ноте и unit interval.
- Null timing MUST иметь обе границы null, пустые intervals и отсутствие note_links.
- Validator MUST отклонить перекрывающиеся активные интервалы разных units ведущего голоса; касание границ допускается.
- Mapper MUST сохранять временной порядок units внутри occurrence; конфликтующие автоматические варианты остаются только unresolved-кандидатами.
- Normalizer MUST строить note_link-интервалы из оставшихся связей, сохраняя независимые unpitched-интервалы; у первой связи continuation=false, у последующих true.
- Editor MUST сохранять unit без связей в unresolved; при пустых intervals он становится unplaced. Undo восстанавливает связи, интервалы и продолжения.
- Renderer MUST использовать единый действующий документ: опубликованная база плюс её сохранённая ручная ревизия; отдельная словесная полка исключена.
- Операции split/merge MUST сохранять происхождение, создавать новые unit IDs и атомарно перепривязывать связи; undo восстанавливает прежние ID.
- Merge MUST сохранять реальные паузы массивом intervals; разрыв не превращается в протяжённую ноту.
- Редактор MUST менять только текст и связи; исходные NoteEvent, F0, атаки piano, WAV и tempo остаются неизменными.
- Кеш MUST учитывать SHA входов/нот/CTC, версии builder/mapper и параметры. Ревизия привязана к конкретному ключу базы.
- GET, save, undo и изменение масштаба MUST NOT запускать ASR, CTC, separation, F0 или синтез.
- UI MUST сохранять glyph cache, непрерывное следование и три секунды будущего чтения; мобильная версия исключена.
- Новый основной сценарий MUST исключить строки ролей и автоматическую группировку голосов.
- Legacy adapter MUST NOT превращать целое старое слово или contextual label в подтверждённый слог.
- Publisher MUST проверить payload SHA и схему до переключения index; неполный комплект не публикуется.
## Failure Behavior
1. IF запись не удалась, THEN UI MUST сохранить введённый документ доступным для повторного сохранения и экспорта.
2. IF ревизия устарела, THEN API MUST вернуть 409 с текущей ревизией без перезаписи.
3. IF исходники или нотная база изменились, THEN storage MUST отказать в молчаливом переносе ручных связей.
4. IF модель не дала слоговую разбивку, THEN UI MUST показать fallback и доступную коррекцию.
5. IF времена некорректны, THEN editor MUST сохранить прежние границы и объяснить ошибку.
6. IF новая подготовка прервана, THEN storage MUST сохранить прежнюю готовую базу и ручной документ.
7. IF новая схема неизвестна, THEN reader MUST сообщить несовместимость без изменения файла.
## Conformance
S01–S24 из @docs/syllable-score-v1.md. Существующие точки: @tests/test_syllables.py, @tests/test_v3_storage.py, @tests/test_manual_lyrics.py, @tests/studio_player.test.cjs и @tests/browser_checks.js; тесты score/model/storage и межъязыкового контракта входят в текущий набор проверок.
Программная целостность и пригодность при пении проверяются отдельно. Обе постоянные песни проходят @scripts/check_reference_song.py, результаты остаются в новых вкладках настольного браузера. Сложные наложения оцениваются как ограничение первого этапа.

## Уточнение реализации от 14 сентября 2026 года

Проверочные песни заменены на Sputnik — You Shaped Hole in My Heart (198 слов, en) и Mujuice — Журавли (Misha Mishenko Remix) (118 слов, ru). Seekae/Abracadabra через анализ не запускать; их файлы и историю сохранить. Новые MP3/RTF/TXT и результаты хранятся локально вне Git.

Исходные нотные связи партии адресуют неизменяемый опубликованный набор полной мелодии, который уже отображает студия и использует пианино. У learning-v3 stable notes и первичного melody.json разные ID; замена видимых нот первичными ради подписей нарушила бы сохранение мелодии. SHA набора full notes и ключ опубликованной базы фиксируются вместе с партией. Изменение слогов не меняет этот набор или атаки пианино.

## Временной порядок при ручном переназначении

Порядок units одного occurrence определяется началом первого активного интервала. Переназначение средней связи распева сохраняет старый unit_id и остальные связи до/после выбранного участка. Охватывающий start/end не доказывает пересечение: проверяются только реальные intervals. Это позволяет одной отменяемой операцией назначить выбранной области другой слог без скрытого создания нового исполнения слова.

## Ограничения реализованной версии

Реализовано в @src/karaoke_generator/syllable_score.py, @src/karaoke_generator/syllable_score_storage.py, @src/karaoke_generator/syllable_score_web.py и static/syllable-*. Сводка проверок: @docs/syllable-score-verification.md. Слоговые кандидаты остаются приблизительными; отсутствие пригодной ноты сохраняется как unresolved/unplaced.

Старая ручная база воспроизводит собственный проверенный снимок notes/piano. Если опубликованная полная мелодия уже другая, скорости кроме 1× временно недоступны: темпо текущей базы не подставляется к старой. Исходные файлы сохранены. Для одинаковой текущей базы доступны .25/.5/1/2×.

Допускается различие производных источников темпо ровно на один последний sample из-за округления длины при синтезе: нормализуются только копии входов RubberBand, оригиналы не меняются. Большие расхождения и усечённый PCM отвергаются. Ключи кеша для одинаковых длин сохранены.

## Приёмка пользователем и дальнейшая работа

14 сентября 2026 года пользователь подтвердил, что реализация работает хорошо, и поручил перенести её в основной локальный проект, закоммитить и запушить. Текущий сценарий принят для использования. Дальнейшая проработка внешнего вида и взаимодействия при редактировании слогов отложена отдельным поручением; она не входит в эту публикацию. Это решение о пригодности текущего продукта, а не измерение фонетической точности всех автоматических границ.
