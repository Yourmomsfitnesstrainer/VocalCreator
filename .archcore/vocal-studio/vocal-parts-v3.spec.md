## Purpose & Scope

Актуальная версия приложения — рабочая демка 0.1 по решению пользователя от 13 сентября 2026 года. Принятая основа `bfd2665` ранее называлась 0.3; `v3` в именах кода, URL и файлов обозначает внутренний формат. Ниже сохранена история этой реализации.

Контракт версии 0.3 по @docs/vocal-studio-tz-v3.md. Старые документы описывают v1/v2; новая рабочая основа содержит их точный снимок. Независимая музыкальная приёмка остаётся открытой.

## Surface

@src/karaoke_generator/syllables.py, @src/karaoke_generator/learning_v3.py, @src/karaoke_generator/v3_storage.py, @src/karaoke_generator/studio_web.py.
`GET /api/studio/jobs/{id}/text`; `POST /api/studio/jobs/{id}/v3/{mode}`; разрешённые GET производных JSON/WAV. `job.v3_modes` перечисляет готовые варианты без запуска подготовки.
Схема 3: canonical_text, words, text_parts, note_text_links, notes[].labels, word_note_links, diagnostics, provenance. Смещения текста выражены в Unicode codepoints; времена — секунды оригинала.

## Normative Behavior

1. При открытии результата reader MUST сохранять каждое вхождение канонического слова, написание, пунктуацию и порядок.
2. При отсутствии времени reader MUST сохранять слово с неопределённым временем и объяснением.
3. При построении частей mapper MUST использовать акустические CTC-границы для внутренних времён.
4. При отсутствии пригодных границ mapper MUST выводить целое слово с причиной fallback.
5. При продолжении части через несколько нот mapper MUST сохранять один part_id.
6. При изменении подписей синтезатор MUST сохранять исходное расписание атак и пауз.
7. При выборе Light, Medium или Pro mapper MUST сохранять все подтверждённые переходы внутри слова.
8. При подготовке storage MUST публиковать только завершённый комплект JSON и piano WAV.
9. При чтении старого результата API MUST оставлять запуск подготовки явному действию пользователя.
10. При проверке CTC storage MUST сверять происхождение текста и фактического вокала.
11. При подготовке версии 0.3 storage MUST использовать отдельный каталог learning-v3.

## Constraints & Invariants

Каноническая лирика отделена от произношения, акустического времени и нот. Предположение о произношении строится по гласным ядрам написания для ru/en; оно не объявляется словарной фонетической транскрипцией. Части имеют статус приблизительности и модельный score, который не является калиброванной вероятностью.
Сейчас три режима используют одинаковые стабильные события: различия без независимой калибровки не имитируются удалением нот. Прежние лимиты одной/двух нот на слово остаются только в v2 API.
Ключ включает байтовые SHA исходных файлов, ASR/CTC-кешей, алгоритмов частей/режимов, версии/параметры сегментации и синтеза. Старые JSON/WAV и learning не переписываются.

## Failure Behavior

1. Если источник CTC относится к другому вокалу, THEN mapper MUST отвергнуть его.
2. Если приблизительный интервал слова аномален, THEN mapper MUST исключить уверенные связи этого слова с нотами.
3. Если подготовка завершается ошибкой, THEN storage MUST сохранить прежний опубликованный комплект.
4. Если временная разметка отсутствует, THEN UI MUST сохранить текст и готовые аудиодорожки.

## Conformance

@tests/test_syllables.py и @tests/test_v3_storage.py: все слова, отсутствующие времена, произношение/CTC, continuation, паузы, отсутствие дополнительных атак, запрет чужого кеша, атомарность и изоляция артефактов. Реальный пример закреплён в @scripts/check_reference_song.py; показатели и ограничения — @docs/vocal-studio-v3-verification.md.

## Восстановление пропущенной лирики

@src/karaoke_generator/lyric_recovery.py восстанавливает привязку полной канонической последовательности через CTC по локальному вокалу. Распознавание, пропустившее повтор припева, не ограничивает набор слов для выравнивания. Подходящие начала куплетов ограничивают области поиска; изолированные и сжатые ASR-интервалы не используются как опоры.

Целые распознанные фразы из трёх и более последовательных слов сопоставляются с ближайшим акустическим вхождением строки, с сохранением ID каждого повтора. Цепочка через большой пропуск ASR отвергается. Ручные границы сохраняются; пригодные локальные границы сохраняются при согласии независимого CTC по началу слова. Новые времена имеют признак приблизительности и сохраняют original_timing.

Производные свидетельства хранятся в lyric-recovery-v3. Ключ учитывает вокал, полный текст с ID вхождений, распознанные слова, опоры куплетов, границы вокальной активности, код и версии библиотек. Полезная нагрузка защищена SHA; исходные alignment.json, lyrics.txt, WAV и результаты v2 не изменяются.

Если интервалы слова и ноты немного расходятся, подпись продлевается до границы нотного события с признаком приблизительности. При большом расстоянии отображается явно обозначенный контекст лирики, а не подтверждённая акустическая привязка. Наличие подписи контекста MUST NOT считаться распознаванием слова. Без пригодного временного свидетельства исходный текст остаётся в полной лирике.

@tests/test_lyric_recovery.py проверяет пропущенные повторы, выбор ближайшего акустического вхождения фразы, запрет переноса через ASR-пропуски, ручные границы, повреждённый кеш и отказ модели. Отчёт об исправлении — @docs/vocal-studio-text-repair-verification.md.

## Приёмка версии 0.3 — 13 сентября 2026 года

Пользователь принял текущий результат на постоянной песне и поручил зафиксировать его без дополнительных изменений в ветке `version-0.3` с включением в `master`. Принятый снимок включает реализацию v2, части слов v3 и исправление пропусков лирики.

На проверенном примере сохранены 305 канонических вхождений и 771 нота; пустых подписей нет. У 130 нот показан явно обозначенный контекст, у 9 слов нет определённой ноты. Эти ограничения входят в принятый снимок; общая независимая акустическая приёмка Q2–Q5 остаётся открытой.

Последняя проверка принятого кода: 170 Python-тестов, 24 JS-теста, 9 групп настоящего браузера и 7 целевых fault probes. Свидетельства и границы результата: @docs/vocal-studio-text-repair-verification.md.
